## 2026-06-05 — Initial build: Phases 0–6

The platform went from `create-next-app` scaffold to a working end-to-end product in a single day: Next.js App Router + TypeScript foundation, Supabase schema + RLS, the manifest-driven generation pipeline, the Studio (chat + live preview), credit ledger + Stripe packs, ZIP export, and a first mobile-responsive pass. `archiver` was swapped for `jszip` early on for Turbopack/ESM compatibility (`cd420b0`).

## 2026-08-04 — Changelog cache fix (V1)

The `/changelog` page was found to be serving stale content: it used `revalidate = 300` (5-minute ISR) and the admin write endpoints weren't calling `revalidatePath('/changelog')` after mutations, so new/edited entries could take up to 5 minutes to appear, and DB errors were being silently swallowed into the static JSON fallback with no visibility. Commit `3d616ff` fixed the revalidation gap, stopped swallowing DB errors, and added an edit capability plus a tag whitelist to the admin UI. This is referred to as **changelog V1** in `ClaudeInfoQuante.md`.

Explicitly out of scope for this whole session: `git push` to `main`, running any SQL migration against the production Supabase DB, anything that moves real money or changes production pricing, and `allow_cowork_file_delete` (already established as unavailable without the user present).

**Fix 1 — the "wasted auto-deploy" issue** (`app/api/quante/generate/route.ts`, `app/api/quante/iterate/route.ts`, `app/api/quante/fix/route.ts`, `app/api/deploy/route.ts`). Investigation found the actual mechanism was worse than the one-line description in `ClaudeInfoQuante.md` suggested: `createPreviewDeployment()` — despite its name — deploys with `target: 'production'` *and* attaches the store's public subdomain. Every first-time generation, and every chat iteration or auto-fix attempt made *before* the merchant's first "Push to Live" click, was silently doing a full production Vercel build and making the subdomain publicly reachable, while StudioClient always hides that build behind the "Push to Live" screen (`showPushToLive`) regardless. Clicking "Push to Live" then ran a second, fully redundant production build via `/api/deploy` — the only one actually wired up with `QUANTE_API_KEY`, the hosting trial timer, and the real credit debit.

Fix: generate/iterate/fix now check `project.hosting_trial_ends_at` (set exactly once, by `/api/deploy`, on the first real successful "Push to Live") as the "has this store ever gone live" signal. Not yet live → use `createVercelPreviewDeploy()` (a true Vercel preview: no production target, no domain attach) purely to validate the build and drive the self-healing auto-fix loop, which still needs a real deployment's logs to detect build errors. Already live → unchanged, still a full production redeploy so chat edits keep updating the live store. `generate/route.ts` no longer needs a `slug` for its validation deploy at all, since there's no domain to attach.

While tracing this, also found a related latent bug in `/api/deploy` GET (the shared status-polling endpoint, used both for real deploys and, via a fallback path in `StudioClient`'s `EventSource.onerror`, for the free validation/preview deploys too): it started the 30-day hosting trial and debited 5 credits for *any* deployment reaching `ready` through it, regardless of whether it was a real paid production deploy or a free preview. Fixed by gating both behind `if (domain)` — only real production deploys ever set a `domain` on their `deployments` row.

**Fix 2 — shipping/fulfillment secrets stored in plaintext.** `lib/crypto.ts` (AES-256-GCM) already existed and was already used for Comgate/GoPay/PayPal secrets via `/api/project/secrets`, but `app/api/projects/[id]/settings/route.ts` — the route that actually saves Zásilkovna, DHL, GLS, and byrd credentials — never called it, so those fields sat in `project_secrets` as plaintext. Fixed: `settings/route.ts` now encrypts `zasilkovna_api_password`, `dhl_api_key`, `dhl_api_secret`, `gls_password`, `byrd_api_key`, `byrd_api_secret` on write (matching the existing convention of encrypting secrets/passwords but not IDs/usernames — `zasilkovna_api_key` stays plaintext since it's also pushed to the deployed store's public `NEXT_PUBLIC_ZASILKOVNA_API_KEY` env var). The five read sites (`fulfillment/route.ts`, `dhl-shipment/route.ts`, `gls-shipment/route.ts`, both `zasilkovna-shipment/route.ts` routes) now call `decryptSecret()` before using the credentials. `decryptSecret()` passes plaintext through unchanged, so existing rows keep working with no backfill needed — they just won't be encrypted until next saved from the settings form.

**Fix 3 — RLS `auth.uid()` vs `auth.jwt() ->> 'sub'` inconsistency.** New file `supabase/migration-rls-consistency.sql` (not run). Ten policies across `custom_components`, `user_domains` (×4), `store_earnings`, `store_payout_accounts`, `payout_requests` (×2), and `store_orders` still used `auth.uid()::text`, left over from before the Clerk migration standardized on `(auth.jwt() ->> 'sub')`. These currently behave identically (Supabase's Clerk JWT integration maps `sub` into `auth.uid()` too), and since all server code reads through the service-role client anyway, this was never a live access-control gap — but it's a silent trap if that mapping detail ever changes, since RLS denials/misscoping wouldn't surface as an application error. The migration drops and recreates all ten with the canonical pattern; includes a verification query to confirm zero remaining `auth.uid()` policies after applying.

## 2026-08-07 (continued) — byrd fulfillment integration hardening

Main priority of the autonomous session, per `quante-fulfillment-byrd-spec.md`. Before writing anything, checked what already existed: `lib/fulfillment/byrd.ts` + `lib/fulfillment/provider.ts` + `migration-byrd.sql` (from the 07-18 "F2-F9 master build") already implement a basic, working, *manually admin-triggered* byrd integration — `project_secrets.byrd_api_key/byrd_api_secret`, a `createShipment`/`getShipment`-only provider, and `store_orders.fulfillment_provider/fulfillment_ref/fulfillment_status` columns — wired to a single route the merchant clicks a button on. This was never previously documented in `ClaudeInfoQuante.md` (same gap as the changelog system earlier today). The spec's ambitious design (dedicated `store_fulfillment_integrations`/`fulfillment_shipments`/`fulfillment_product_links` tables, full provider abstraction, Stripe-webhook-triggered auto-shipping) was written without knowledge of this existing, simpler, already-shipped implementation.

Decision: extend and harden the real implementation rather than build two parallel byrd integrations. Kept `project_secrets` for credentials (already encrypted as part of today's Fix 2, see above) instead of adding a new `store_fulfillment_integrations` table; kept `store_orders`'s three fulfillment columns as the fast denormalized read the Studio order list already uses, and added `fulfillment_shipments` (source of truth + the idempotency guard) alongside it, kept in sync by a new sync helper.

**Real API contract, not guessed.** Fetched the live docs at developers.getbyrd.com (authentication, how-to-call-the-APIs, frequency/rate-limits, creating-a-shipment + its OpenAPI reference, get-shipment-details, listing-shipments, listing-products, creating-a-product, announcing-returns). Two concrete corrections against the existing `byrd.ts`: (1) byrd wraps every response in `{"data": {...}}` — the old code read fields off the top-level body directly, which would have silently produced `byrd_id: undefined` on every real shipment creation; (2) `POST /v3/shipments` accepts an `ensure_unique_order_id=true` query parameter that makes byrd itself reject a duplicate `order_id` — now used as a second safety net on top of, never instead of, the DB-level `unique(order_id)` guard.

**New module layout**, matching the spec's requested shape (`lib/fulfillment/types.ts` + `registry.ts` + `providers/byrd/{client,mapper,index}.ts`) so a second provider (Skladon, Shipmonk, ...) can be added without touching checkout: domain types shaped to Quante's *actual* schema (`store_orders` rows, `store_inventory` product_id-as-SKU — Quante has no separate products table with a SKU column, documented explicitly since it's a real deviation from a naive generic-spec assumption) rather than the spec's generic `products`/`orders` tables. `client.ts` handles auth (`POST /v2/login`, cheap `POST /v2/refresh_token` renewal before expiry, Supabase-cached token with an in-memory fallback if the migration hasn't run), retry-with-backoff on 429/5xx only (never on shipment creation), and per-request logging. `mapper.ts` is the only place byrd's field-naming conventions (snake_case in v3, camelCase in v2) live.

**The idempotent order → shipment path** (`lib/fulfillment/auto-ship.ts`) — insert a `'creating'` row into `fulfillment_shipments` first; a `23505` unique violation on a second/third attempt for the same order returns `{ outcome: 'duplicate' }` without ever calling byrd again; only a successful insert proceeds to the actual (never-retried) `createShipment()` call. Falls back automatically to the old direct single-attempt behavior if `migration-fulfillment-v2.sql` hasn't run yet, so the existing manual "send to fulfillment" button in the Studio keeps working unchanged either way. **Not wired into the Stripe webhook** — auto-shipping every paid order without a review step is a business-behavior decision, not a bug fix, and was deliberately left as a documented, ready-to-wire follow-up (`buildQuanteOrder()` in the fulfillment route is exported specifically so that wiring is a few lines, not a redesign) rather than made unilaterally.

**Reconciliation** (`app/api/cron/fulfillment-reconcile`, every 15 min): shipments stuck in `'creating'` for over 10 minutes get looked up in byrd by order id; found → adopt the real shipment id (no duplicate created); not found → marked `'failed'`, visible for a manual retry. **Tracking** (`app/api/cron/fulfillment-tracking`, hourly): byrd has no tracking webhook (confirmed against the docs), so this is the only path tracking numbers and the customer email ever go out through — `customer_notified_at` is set only after the send succeeds, matching the same "never email twice" pattern already established for `changelog_entries`. **Stock sync** (`app/api/cron/fulfillment-stock`, every 15 min): writes into the *existing* `store_inventory.stock_qty` column checkout already enforces — no storefront changes needed for byrd-managed stock to actually gate the cart.

**Out of scope for this pass**: the full admin UI from spec section 8 (connection-test button, product-sync table, shipment overview panel, "retry failed" button) was not built — only the API/data layer underneath it (`POST /api/projects/[id]/fulfillment/sync-products`, the existing order-row fulfillment buttons). `announceReturn()` is intentionally left unimplemented (throws a clear error) — byrd's actual `/v3/returns/announce` needs a byrd shipment id + notification email + per-item shipment-item ids, none of which the spec's `announceReturn(orderId, items)` signature carries; documented rather than guessed.

**Tests**: `__tests__/fulfillment-byrd.test.mjs` (`npm run test:fulfillment-byrd`), 19/19 passing — mapper functions (street splitting, response envelope unwrapping, error extraction, tracking extraction) plus the three cases the spec explicitly asks for on the shipment-creation path: duplicate webhook delivery (provider called exactly once across 3 attempts), a provider API failure, and an ambiguous/partial response — all against an inlined fake DB, no live byrd credentials available in this environment to test against.

**Operational note**: the three new cron schedules (hourly + two 15-minute ones) require a Vercel plan that supports sub-daily crons — the existing `/api/cron/hosting` is daily, so this project's current Vercel plan tier for cron frequency should be confirmed before relying on these firing as scheduled.

**To activate, in this order:** (1) run `supabase/migration-fulfillment-v2.sql` against production; (2) `git push`; (3) confirm the Vercel plan supports the new cron frequencies (`vercel.json` already updated); (4) a merchant enters their real byrd API key/secret in Admin → Settings, same UI as before. Everything works with the existing manual button in the interim, with or without the migration — the migration only upgrades the safety/observability underneath it.

### Feature 2 — Partner program for agencies

Before building, read `supabase/schema.sql`'s `credit_ledger` table (the append-only ledger pattern the user asked to mirror), `supabase/migration-agency.sql` + `lib/tier.ts`, and the Stripe webhook (`app/api/stripe/webhook/route.ts`) in full. **Important discovery**: the codebase already has an `'agency'` concept — `users.tier = 'agency'`, gated by `isAgencyUser()` in `lib/tier.ts` — but it's an unrelated thing: a single user's own paid subscription tier that raises their own project limit (`AGENCY_PROJECT_LIMIT`). It has nothing to do with reselling or commissions on other accounts. To avoid confusing the two, the new tables are named `partners`/`partner_*`, not `agency_*`, and the distinction is called out explicitly in the new migration's header comment.

**Explicit money constraint from the user, honored throughout**: build the structure and the commission *calculation*, never a real payout. No code anywhere in this feature calls a Stripe Connect transfer, moves money, or marks a ledger row `'paid'` — that status value exists in the schema for later, but nothing writes it.

**Schema** (`supabase/migration-partners.sql`, **not run**): `partners` (one row per Quante user who registers as a partner — company name, contact email, a generated 8-char referral code, a `commission_rate_bps` capped at 50%, and a `status` of `pending → active → suspended`, admin-gated); `partner_projects` (which projects are assigned to which partner, one partner per project via a UNIQUE constraint); `partner_commission_ledger` (append-only, `balance_after_cents` running total — identical shape/spirit to `credit_ledger` — with `UNIQUE(partner_id, ref_id)` making every insert idempotent). RLS policies use the canonical `(auth.jwt() ->> 'sub')` pattern from the earlier RLS-consistency fix, not `auth.uid()`.

**Assignment model — a design decision flagged for the user to revisit**: a partner can only assign projects **they themselves own** (`projects.user_id = partners.user_id`). This models "an agency builds a client's store inside their own Quante account" — the agency owns the project and earns commission on it. It does *not* model "a partner refers a separately-owned client account," which would need a consent/invitation flow on the client's side. The `referral_code` column is reserved for that future flow but nothing wires it into signup yet — deliberately left as documented, ready infrastructure rather than guessed at.

**Commission calculation** (`lib/partner-commission.ts`, dependency-light — only imports `supabaseAdmin`, so `calculateCommissionCents()` is directly unit-testable): `calculateCommissionCents(amountCents, bps)` floors rather than rounds, and `recordCommission()` does the same read-last-balance-then-insert pattern as `credit_ledger` writes elsewhere in this codebase, catching a `23505` unique-violation on `(partner_id, ref_id)` as "already recorded, not an error" — the same idempotency convention established during the byrd fulfillment work. `getActivePartnerForProject()` looks up whether a project has an active assignment to an active (admin-approved) partner.

**Wired into the live Stripe webhook's hosting-subscription branch** (`customer.subscription.created/updated`, the existing `else` branch that upserts `hosting_subscriptions`): when a subscription goes `active` for a project with an active partner assignment, pulls the price off `sub.items.data[0].price` and calls `recordCommission()` with `ref_id = "${subscriptionId}:${periodEnd}"` — one entry per billing period, so recurring renewals each accrue commission exactly once even though Stripe fires multiple `updated` events per subscription lifecycle. **Wrapped in its own `try/catch` that only logs** — a bug or outage in the partner-commission code can never break the real webhook path that credits users' hosting and redeploys suspended stores. This is the one place this feature touches genuinely live, already-in-production code; everything else is new, inert files until the migration is run.

**API**: `POST /api/partners/register` (self-serve, status starts `pending`, retries on referral-code collision), `GET /api/partners/me` (own partner record + assigned projects + last 20 ledger entries + running balance), `POST` / `DELETE /api/partners/projects` (assign/unassign one's own project, ownership-checked both ways), `POST /api/admin/partners/[id]/status` (admin approval gate, reusing the exact `ADMIN_EMAILS` pattern from `app/api/admin/changelog/route.ts` rather than inventing a new one). No Studio UI was requested for this feature (unlike Store Health Score) — the user's ask was schema + API only.

Verified `tsc --noEmit` (0 errors) and `eslint` on every new/touched file (0 errors/warnings). Re-ran all five prior test suites (whitelabel, changelog, changelog-webhook, fulfillment-byrd, store-health) — all still pass, confirming this feature didn't regress anything, including the Stripe webhook it edits.

### Feature 3 — Marketplace for components & starter stores

Before building, read `supabase/migration-custom-components.sql` in full (the table being "opened up" — confirmed it's project-scoped with no existing cross-user concept, so genuinely new tables were required, not just a flag on the existing table) and re-checked the RLS-consistency fix from earlier in this session to use the canonical `(auth.jwt() ->> 'sub')` pattern in the new policies. Useful safety property discovered while reading `custom_components`: its `code` column only ever holds output from the AI component-generation pipeline described in `CLAUDE.md` §4.3 — sandboxed, no network calls, no arbitrary imports, allowlisted primitives only, validated before ever being saved — so a `custom_components` row with `passed_validation = true` is already reasonably safe to let another user install into their own project. A full `code_versions.files` export (the "starter store" case) has no equivalent automated validation, so those are treated more cautiously (see below).

**Explicit money constraint, honored identically to Feature 2**: "purchasing" is bookkeeping only — a `marketplace_purchases` row + a `marketplace_seller_ledger` entry — and installs a copy of the content. No code here charges a real payment method, calls Stripe, or moves money. This is the one spot in the whole session with the least room for ambiguity about what "not live" means, so it's called out three times in comments (migration header, `lib/marketplace.ts` header, the purchase route's own header) that in production this endpoint should be invoked only after a real charge succeeds — e.g. from the Stripe webhook, the exact same way credit-pack purchases already work — and that wiring is a deliberate activation step, not done here.

**Schema** (`supabase/migration-marketplace.sql`, **not run**): `marketplace_listings` (a **snapshot**, not a live reference, to `custom_components.code` or `code_versions.files` — so edits to the original after publishing never retroactively change a listing already on sale, and buyers who already purchased keep what they paid for; `passed_validation` copied from the source component controls auto-listing vs. requiring admin review); `marketplace_purchases` (one per listing+buyer via a UNIQUE constraint, price/fee frozen at purchase time so later listing-price changes can't retroactively affect past sales); `marketplace_seller_ledger` (append-only, running balance, `UNIQUE(purchase_id)` for idempotency — same shape as `credit_ledger` and `partner_commission_ledger`).

**Listing approval gate**: `kind='component'` listings snapshotted from an already-`passed_validation=true` custom component are auto-`status='listed'` — they already went through the sandboxed validator once. Everything else — unvalidated components, and *every* `kind='starter_store'` listing (a full code export has no automated validation today) — starts `status='pending'` and needs an admin to approve it via `POST /api/admin/marketplace/listings/[id]/status`, reusing the exact `ADMIN_EMAILS` gate from `app/api/admin/changelog/route.ts` and the new partner-status endpoint, rather than inventing a third pattern.

**Calculation** (`lib/marketplace.ts`, dependency-light like `lib/partner-commission.ts`): `calculateRevenueSplit(priceCents, platformFeeBps)` — floors, clamps the fee to [0, 100%], defaults to a 20% platform cut (`DEFAULT_PLATFORM_FEE_BPS`) per "Quante si bere procento" in `CLAUDE.md`. `recordSellerEarning()` is the same read-last-balance-then-insert-with-idempotent-unique-constraint pattern used everywhere else money-adjacent in this codebase.

**API**: `GET/POST /api/marketplace/listings` (public browse of `status='listed'` only — metadata fields, never the snapshot/code; publish endpoint branches on `kind`, ownership-checked against `custom_components`→`projects` or `projects` directly), `GET /api/marketplace/listings/[id]` (detail — `snapshot` is stripped from the response unless the caller is the seller or already purchased it, so browsing never leaks source before payment), `POST /api/marketplace/purchases` (records the purchase + seller earning, then **installs**: for a component, inserts a new `custom_components` row into the buyer's chosen project with a fresh `market-<id>` ref to avoid the `(project_id, ref)` collision; for a starter store, inserts a new `code_versions` row — same mechanism `iterate`/`generate` already use for versioning), `GET /api/marketplace/mine` (own listings of any status + seller ledger/balance + purchase history as a buyer), `POST /api/admin/marketplace/listings/[id]/status` (admin review gate).

**UI** — the user's ask for this feature was explicitly "basic UI for browsing," so that's what was built, not a full publish workflow: new `app/(app)/marketplace/page.tsx` (server component, fetches `status='listed'` listings + which ones the signed-in user already owns) + `MarketplaceBrowser.tsx` (client component — a responsive card grid, kind badge, price, a project picker populated from the existing `GET /api/projects`, and a "Buy & install" flow that calls the purchase endpoint and flips the card to an "Installed" state). Added a "Marketplace" entry to the shared app-shell nav (`app/(app)/layout.tsx`'s `NAV` array) so it's actually reachable — a small, low-risk, additive change to an already-live file. Verified `tsc --noEmit` (0 errors) and `eslint` (0 errors/warnings) across every new/touched file, including the shared `layout.tsx` nav edit.
