## 2026-08-04 — Changelog cache fix (V1)

The `/changelog` page was found to be serving stale content: it used `revalidate = 300` (5-minute ISR) and the admin write endpoints weren't calling `revalidatePath('/changelog')` after mutations, so new/edited entries could take up to 5 minutes to appear, and DB errors were being silently swallowed into the static JSON fallback with no visibility. Commit `3d616ff` fixed the revalidation gap, stopped swallowing DB errors, and added an edit capability plus a tag whitelist to the admin UI. This is referred to as **changelog V1** in `ClaudeInfoQuante.md`.

Explicitly out of scope for this whole session: `git push` to `main`, running any SQL migration against the production Supabase DB, anything that moves real money or changes production pricing, and `allow_cowork_file_delete` (already established as unavailable without the user present).

**Fix 1 — the "wasted auto-deploy" issue** (`app/api/quante/generate/route.ts`, `app/api/quante/iterate/route.ts`, `app/api/quante/fix/route.ts`, `app/api/deploy/route.ts`). Investigation found the actual mechanism was worse than the one-line description in `ClaudeInfoQuante.md` suggested: `createPreviewDeployment()` — despite its name — deploys with `target: 'production'` *and* attaches the store's public subdomain. Every first-time generation, and every chat iteration or auto-fix attempt made *before* the merchant's first "Push to Live" click, was silently doing a full production Vercel build and making the subdomain publicly reachable, while StudioClient always hides that build behind the "Push to Live" screen (`showPushToLive`) regardless. Clicking "Push to Live" then ran a second, fully redundant production build via `/api/deploy` — the only one actually wired up with `QUANTE_API_KEY`, the hosting trial timer, and the real credit debit.

Fix: generate/iterate/fix now check `project.hosting_trial_ends_at` (set exactly once, by `/api/deploy`, on the first real successful "Push to Live") as the "has this store ever gone live" signal. Not yet live → use `createVercelPreviewDeploy()` (a true Vercel preview: no production target, no domain attach) purely to validate the build and drive the self-healing auto-fix loop, which still needs a real deployment's logs to detect build errors. Already live → unchanged, still a full production redeploy so chat edits keep updating the live store. `generate/route.ts` no longer needs a `slug` for its validation deploy at all, since there's no domain to attach.

While tracing this, also found a related latent bug in `/api/deploy` GET (the shared status-polling endpoint, used both for real deploys and, via a fallback path in `StudioClient`'s `EventSource.onerror`, for the free validation/preview deploys too): it started the 30-day hosting trial and debited 5 credits for *any* deployment reaching `ready` through it, regardless of whether it was a real paid production deploy or a free preview. Fixed by gating both behind `if (domain)` — only real production deploys ever set a `domain` on their `deployments` row.

**Fix 2 — shipping/fulfillment secrets stored in plaintext.** `lib/crypto.ts` (AES-256-GCM) already existed and was already used for Comgate/GoPay/PayPal secrets via `/api/project/secrets`, but `app/api/projects/[id]/settings/route.ts` — the route that actually saves Zásilkovna, DHL, GLS, and byrd credentials — never called it, so those fields sat in `project_secrets` as plaintext. Fixed: `settings/route.ts` now encrypts `zasilkovna_api_password`, `dhl_api_key`, `dhl_api_secret`, `gls_password`, `byrd_api_key`, `byrd_api_secret` on write (matching the existing convention of encrypting secrets/passwords but not IDs/usernames — `zasilkovna_api_key` stays plaintext since it's also pushed to the deployed store's public `NEXT_PUBLIC_ZASILKOVNA_API_KEY` env var). The five read sites (`fulfillment/route.ts`, `dhl-shipment/route.ts`, `gls-shipment/route.ts`, both `zasilkovna-shipment/route.ts` routes) now call `decryptSecret()` before using the credentials. `decryptSecret()` passes plaintext through unchanged, so existing rows keep working with no backfill needed — they just won't be encrypted until next saved from the settings form.

**Fix 3 — RLS `auth.uid()` vs `auth.jwt() ->> 'sub'` inconsistency.** New file `supabase/migration-rls-consistency.sql` (not run). Ten policies across `custom_components`, `user_domains` (×4), `store_earnings`, `store_payout_accounts`, `payout_requests` (×2), and `store_orders` still used `auth.uid()::text`, left over from before the Clerk migration standardized on `(auth.jwt() ->> 'sub')`. These currently behave identically (Supabase's Clerk JWT integration maps `sub` into `auth.uid()` too), and since all server code reads through the service-role client anyway, this was never a live access-control gap — but it's a silent trap if that mapping detail ever changes, since RLS denials/misscoping wouldn't surface as an application error. The migration drops and recreates all ten with the canonical pattern; includes a verification query to confirm zero remaining `auth.uid()` policies after applying.

## 2026-08-07 (continued) — byrd fulfillment integration hardening

Main priority of the autonomous session, per `quante-fulfillment-byrd-spec.md`. Before writing anything, checked what already existed: `lib/fulfillment/byrd.ts` + `lib/fulfillment/provider.ts` + `migration-byrd.sql` (from the 07-18 "F2-F9 master build") already implement a basic, working, *manually admin-triggered* byrd integration — `project_secrets.byrd_api_key/byrd_api_secret`, a `createShipment`/`getShipment`-only provider, and `store_orders.fulfillment_provider/fulfillment_ref/fulfillment_status` columns — wired to a single route the merchant clicks a button on. This was never previously documented in `ClaudeInfoQuante.md` (same gap as the changelog system earlier today). The spec's ambitious design (dedicated `store_fulfillment_integrations`/`fulfillment_shipments`/`fulfillment_product_links` tables, full provider abstraction, Stripe-webhook-triggered auto-shipping) was written without knowledge of this existing, simpler, already-shipped implementation.

Decision: extend and harden the real implementation rather than build two parallel byrd integrations. Kept `project_secrets` for credentials (already encrypted as part of today's Fix 2, see above) instead of adding a new `store_fulfillment_integrations` table; kept `store_orders`'s three fulfillment columns as the fast denormalized read the Studio order list already uses, and added `fulfillment_shipments` (source of truth + the idempotency guard) alongside it, kept in sync by a new sync helper.

**Real API contract, not guessed.** Fetched the live docs at developers.getbyrd.com (authentication, how-to-call-the-APIs, frequency/rate-limits, creating-a-shipment + its OpenAPI reference, get-shipment-details, listing-shipments, listing-products, creating-a-product, announcing-returns). Two concrete corrections against the existing `byrd.ts`: (1) byrd wraps every response in `{"data": {...}}` — the old code read fields off the top-level body directly, which would have silently produced `byrd_id: undefined` on every real shipment creation; (2) `POST /v3/shipments` accepts an `ensure_unique_order_id=true` query parameter that makes byrd itself reject a duplicate `order_id` — now used as a second safety net on top of, never instead of, the DB-level `unique(order_id)` guard.

**New module layout**, matching the spec's requested shape (`lib/fulfillment/types.ts` + `registry.ts` + `providers/byrd/{client,mapper,index}.ts`) so a second provider (Skladon, Shipmonk, ...) can be added without touching checkout: domain types shaped to Quante's *actual* schema (`store_orders` rows, `store_inventory` product_id-as-SKU — Quante has no separate products table with a SKU column, documented explicitly since it's a real deviation from a naive generic-spec assumption) rather than the spec's generic `products`/`orders` tables. `client.ts` handles auth (`POST /v2/login`, cheap `POST /v2/refresh_token` renewal before expiry, Supabase-cached token with an in-memory fallback if the migration hasn't run), retry-with-backoff on 429/5xx only (never on shipment creation), and per-request logging. `mapper.ts` is the only place byrd's field-naming conventions (snake_case in v3, camelCase in v2) live.

**The idempotent order → shipment path** (`lib/fulfillment/auto-ship.ts`) — insert a `'creating'` row into `fulfillment_shipments` first; a `23505` unique violation on a second/third attempt for the same order returns `{ outcome: 'duplicate' }` without ever calling byrd again; only a successful insert proceeds to the actual (never-retried) `createShipment()` call. Falls back automatically to the old direct single-attempt behavior if `migration-fulfillment-v2.sql` hasn't run yet, so the existing manual "send to fulfillment" button in the Studio keeps working unchanged either way. **Not wired into the Stripe webhook** — auto-shipping every paid order without a review step is a business-behavior decision, not a bug fix, and was deliberately left as a documented, ready-to-wire follow-up (`buildQuanteOrder()` in the fulfillment route is exported specifically so that wiring is a few lines, not a redesign) rather than made unilaterally.

**Reconciliation** (`app/api/cron/fulfillment-reconcile`, every 15 min): shipments stuck in `'creating'` for over 10 minutes get looked up in byrd by order id; found → adopt the real shipment id (no duplicate created); not found → marked `'failed'`, visible for a manual retry. **Tracking** (`app/api/cron/fulfillment-tracking`, hourly): byrd has no tracking webhook (confirmed against the docs), so this is the only path tracking numbers and the customer email ever go out through — `customer_notified_at` is set only after the send succeeds, matching the same "never email twice" pattern already established for `changelog_entries`. **Stock sync** (`app/api/cron/fulfillment-stock`, every 15 min): writes into the *existing* `store_inventory.stock_qty` column checkout already enforces — no storefront changes needed for byrd-managed stock to actually gate the cart.

**Out of scope for this pass**: the full admin UI from spec section 8 (connection-test button, product-sync table, shipment overview panel, "retry failed" button) was not built — only the API/data layer underneath it (`POST /api/projects/[id]/fulfillment/sync-products`, the existing order-row fulfillment buttons). `announceReturn()` is intentionally left unimplemented (throws a clear error) — byrd's actual `/v3/returns/announce` needs a byrd shipment id + notification email + per-item shipment-item ids, none of which the spec's `announceReturn(orderId, items)` signature carries; documented rather than guessed.

**Tests**: `__tests__/fulfillment-byrd.test.mjs` (`npm run test:fulfillment-byrd`), 19/19 passing — mapper functions (street splitting, response envelope unwrapping, error extraction, tracking extraction) plus the three cases the spec explicitly asks for on the shipment-creation path: duplicate webhook delivery (provider called exactly once across 3 attempts), a provider API failure, and an ambiguous/partial response — all against an inlined fake DB, no live byrd credentials available in this environment to test against.

**Operational note**: the three new cron schedules (hourly + two 15-minute ones) require a Vercel plan that supports sub-daily crons — the existing `/api/cron/hosting` is daily, so this project's current Vercel plan tier for cron frequency should be confirmed before relying on these firing as scheduled.

**To activate, in this order:** (1) run `supabase/migration-fulfillment-v2.sql` against production; (2) `git push`; (3) confirm the Vercel plan supports the new cron frequencies (`vercel.json` already updated); (4) a merchant enters their real byrd API key/secret in Admin → Settings, same UI as before. Everything works with the existing manual button in the interim, with or without the migration — the migration only upgrades the safety/observability underneath it.

## 2026-08-08 — Generation resilience Level 1: durable checkpointing for `/api/quante/generate`

**Context:** diagnosed (this session) that a device turning off or losing connection mid-generation loses ALL work with no recovery — the entire generation (Claude call, parsing, DB save) runs inside one serverless function invocation, and nothing is persisted until the very last step. See the diagnosis further up this conversation for the full breakdown; this is the first of three approved fix levels, in order: **Level 1 (this entry) → Level 2 (client reconnect) → Level 3 (background job architecture)**. Note this directly realizes brainstorm idea #1 in the NÁPADY section below ("přesunout generaci... na frontu background jobů") — Level 1 is the durable-storage foundation that idea depends on; Levels 2/3 build the rest of it.

**What Level 1 does:** a new `generation_jobs` row is created the moment a generation actually starts (right after the credit/rate-limit/project-limit guard clauses pass, before the first Claude call) and is updated periodically as the stream progresses — piggybacked on the existing 15s keepalive-ping cadence, so no new timer was added. A crash any time after the first tick now loses at most ~15s of generated output instead of the whole generation, even though the *final* code_versions save still only happens once, at the end (Level 1 is about not losing in-flight progress to a checkpoint table — it does not yet make the generation itself resumable from the client; that's Level 3).

**New file — `supabase/migration-generation-jobs.sql`** (NOT run against production, file only): `generation_jobs` table — `id`, `user_id`, `project_id` (nullable — filled in once a brand-new project is created partway through), `brief`, `status` (`running`/`completed`/`failed`), `model_used`, `raw_output` (full accumulated text, checkpointed), `files` (jsonb — only *complete* `<file>` blocks extracted so far), `summary`, `error`, `code_version_id`, `credits_debited`, timestamps. RLS via the canonical `(auth.jwt() ->> 'sub') = user_id` pattern (migration-rls-consistency.sql convention, not `auth.uid()`). This table is also the schema Level 3's polling endpoint will read from — designed with that reuse in mind rather than as a throwaway checkpoint table.

**New file — `lib/generation-checkpoint.ts`**: `extractFileBlocks(raw)` — the single source of truth for "what complete files exist in this raw output so far," shared between the route's final `parseCodeOutput()` (which then validates the 4 `CORE_FILES` are present) and the periodic in-flight checkpoint (no validation, tolerant of a trailing not-yet-closed `<file>` block, which is simply omitted rather than erroring). `filesChanged(a, b)` — cheap diff helper for future use (not yet called anywhere; kept for Level 3's polling endpoint to decide when a client-visible update actually happened).

**Changed — `app/api/quante/generate/route.ts`**:
- `parseCodeOutput()` now delegates file-extraction to `extractFileBlocks()` instead of its own inline regex (behavior unchanged, single source of truth).
- Creates the `generation_jobs` row via the existing user-scoped `supabase` client (same one already used for `projects`/`code_versions` in this route) right before `send({type:'status', text:'Designing your store…'})`. If the insert itself fails, generation proceeds anyway with `jobId = null` — every checkpoint/fail/complete helper below no-ops when `jobId` is null, so checkpointing is a resilience add-on, never a hard dependency of generation working at all.
- Sends a new `{type: 'job', jobId}` event to the client right after the row is created — not consumed by anything yet (Level 2/3 will use it), harmless no-op for the current client.
- `checkpoint(rawOutput, modelUsed)` — called at the same 15s cadence as the existing keepalive ping, in both the primary and fallback model loops. Skips the DB write if `rawOutput.length` hasn't changed since the last checkpoint (cheap guard against pointless round-trips).
- `failJob(message)` — called on every existing early-return error path *after* the job row exists (parse failure, project-creation failure, code_versions-save failure). Early exits *before* job creation (insufficient credits, rate limit, project limit, missing brief, unauthorized) correctly never touch this table — no job ever started.
- `completeJob(...)` — called immediately after the `code_versions` insert succeeds, before credit debit or preview deploy run. This is deliberate ordering: "code durably saved" and "job marked completed" happen together, so the checkpoint status can never lag behind what's actually safe.
- `markCreditsDebited()` — best-effort flag set after a successful credit debit; existing debit-failure handling (silent no-refund-needed-because-never-charged behavior) is unchanged.

**Verification:** `npx tsc --noEmit` clean, 0 errors. `eslint` clean on both changed/new files (`app/api/quante/generate/route.ts`, `lib/generation-checkpoint.ts`) — a full-project `eslint .` run timed out in this sandbox (large project, not indicative of an error in these files specifically). New `__tests__/generation-checkpoint.test.mjs` (`npm run test:generation-checkpoint`) — 12 tests covering `extractFileBlocks` (empty input, single/multiple complete files, trailing incomplete block omitted not erroring, before/after the closing tag, statelessness across repeated calls on a growing string, exact newline-trimming behavior) and `filesChanged` (5 cases). Full existing suite re-run (`node --test __tests__/*.test.mjs`) — all 89 tests pass (77 pre-existing + 12 new), no regressions.

**What Level 1 deliberately does NOT do** (by design — these are Level 2 and Level 3's job): does not let the client resume/view a checkpointed generation after a reload (no read endpoint yet); does not make the generation itself survive the client's HTTP connection actually closing (still one function, one request, per the earlier diagnosis) — it only guarantees that *whatever progress existed* is durably saved every ~15s, so Level 3's background-job version has real data to resume from instead of starting the checkpointing mechanism from scratch.

**Files:** new — `supabase/migration-generation-jobs.sql`, `lib/generation-checkpoint.ts`, `__tests__/generation-checkpoint.test.mjs`. Changed — `app/api/quante/generate/route.ts`, `package.json` (new `test:generation-checkpoint` script).

## 2026-08-08 — Generation resilience Level 2: client-side reconnect after a reload

**Context:** second of the three approved fix levels (Level 1 → **Level 2 (this entry)** → Level 3). Level 1 made in-flight generation progress durable server-side; Level 2 gives the *client* a way to notice, after a reload/crash, that a generation it started may have kept going (or finished) without it — instead of the page just silently resetting to a blank chat with no memory of what happened.

**What Level 2 does:** the moment `handleGenerate()` starts, a small marker (`{startedAt, brief, projectName, jobId}`) is written to `localStorage` under `quante:pending-generation`. It's updated in place once Level 1's new `{type:'job', jobId}` stream event arrives (carrying the `generation_jobs` row id — not consumed yet, kept for Level 3), and removed on every terminal outcome reached *within the same page load*: the `done`/`error` stream events, and both existing recovery paths (the 290s give-up timer and the "stream ended without done" fallback) that already exist in this file. If none of those run — reload, tab/browser closed, device died — the marker survives in `localStorage`, which is exactly the case Level 2 is for.

On mount, `app/(app)/new/page.tsx` now checks for that marker. A marker older than 10 minutes (well past the 300s server hard-cap plus the client's own 290s give-up window) is treated as abandoned and silently discarded — not worth interrupting a fresh visit over. A recent one triggers an automatic `GET /api/projects` check, filtering for a project created after the marker's `startedAt` (minus a 10s clock-skew buffer) — more precise than the existing "last 6 minutes" heuristic used elsewhere in this file, since the exact start time is now known from the marker instead of guessed from "now."

**New UI — resume banner** (top of `/new`, shown whenever a marker is present, independent of `chat`/`ready` stage): shows a truncated preview of the original brief, and:
- If the check found a matching project → **"A generation from before your last reload finished." + "Open finished store →"** button, navigating straight to `/project/:id`.
- If not (yet) found → **"A generation was still running when this page last closed or reloaded." + "Check status"** button, which re-runs the same `/api/projects` check on demand (no auto-polling loop in Level 2 — that's Level 3's job once generation is a real background job worth polling).
- Either way, a **"Discard, start fresh"** button clears the marker and hides the banner, letting the user ignore it and start a new brief.

Starting a *new* generation while an old resume banner is showing clears the stale banner state immediately (the new marker being written makes the old one moot regardless of what it pointed to).

## 2026-08-11 — Generation resilience Level 3: background job architecture, decoupled from the client connection

**Context:** third and final of the three approved fix levels (Level 1 → Level 2 → **Level 3, this entry**). Levels 1–2 made in-flight progress durable and gave a reloaded page a way to notice a past generation — but the core problem from the original diagnosis was still unsolved: generation itself still ran inside the one serverless function invocation handling the client's HTTP request, so if that connection died mid-request (device off, network drop, tab closed), the function was killed by the platform regardless of what had been checkpointed. Level 3 removes that dependency entirely.

**Architecture decision:** used Next.js's `after()` API (stable, `next/server`, confirmed available in this project's Next.js 16.2.7 via direct introspection) instead of standing up a queue service (Inngest etc.). `after()` schedules a callback to keep running *after* the HTTP response has already been sent — the client gets an immediate response, and the actual generation work continues in the same function invocation, invisible to and independent of whether the client is still connected. This fully covers the realistic failure window: generation is inherently bounded to ≤300s (`maxDuration`) regardless of whether a client is present, so "the client disconnects sometime during that window" — the actual scenario from the diagnosis — is now completely handled without any new account, API key, or external service. The one honest caveat (device off for many minutes, well past when the background function itself would have finished or been killed anyway) doesn't change this: nothing running *inside* Vercel's own 300s ceiling can outlast that ceiling, queue-based or not, so `after()` gives the same effective guarantee as a queue would for this specific problem, at far less complexity. No Inngest/queue scaffold was built — it wasn't needed for what was actually being fixed.

**Changed — `app/api/quante/generate/route.ts` (full rewrite):** the old version returned a long-lived NDJSON stream that the client read chunk-by-chunk for the entire generation. Now: `POST` does the fast synchronous work only — validate the brief, auth, credit balance, rate limit, project limit (all via the user-scoped, RLS-enforced `supabase` client) — creates a `generation_jobs` row (`status: 'running', phase: 'designing'`; **this insert is now load-bearing**, unlike Level 1 where it was best-effort, since the job row is the only channel back to the client), schedules the entire generation via `after(() => runGeneration(...))`, and returns `202 {jobId, projectId}` immediately. `runGeneration()` contains everything the old inline logic did — primary Claude stream with the existing 240s soft-timeout/abort/partial-file-recovery logic, fallback-model retry, parsing, project/code_versions save, credit debit, and the post-save preview-deploy validation — restructured around a `setPhase()`/`checkpoint()`/`failJob()` closure trio that writes to `generation_jobs` via `supabaseAdmin` (service-role, not the user-scoped client — deliberate: once the response has been sent, there's no live request/cookie context to justify using the RLS-bound client, and `supabaseAdmin` removes any ambiguity about it). Checkpointing cadence tightened from Level 1's 15s to 4s, since there's no longer a client-facing keepalive ping constraining it. The whole function is wrapped in one top-level `try/catch` so an unexpected error always reaches `failJob()` and the job never hangs in `running` forever.

**New file — `app/api/quante/generate/status/route.ts`:** `GET ?jobId=...`, the only channel a client has into the background job. Reads `generation_jobs` through the user-scoped Supabase client (not `supabaseAdmin`) so RLS is the real access control — a `jobId` belonging to someone else and one that doesn't exist both come back as "no row," which is the correct non-enumerable behavior for a status lookup. Returns `status`, `phase`, `files`, the last 3000 chars of `raw_output` (`rawOutputTail`, enough for the "live code" preview panel without shipping the whole accumulated output on every poll), `summary`, `error`, and `projectId`/`deploymentId`/`previewUrl`/`codeVersionId`.

**New file — `lib/generation-poll.ts`:** the shared, pure decision logic between the poll response and every polling client — `JobStatusPayload`/`PollDecision` types, `decidePollAction(payload)` (running → `continue`; completed with a `projectId` → `navigate`; completed without one → defensive `error`, since silently navigating to `/project/null` would be worse than surfacing a message; failed → `error` with the server's message or a generic fallback), `phaseToStatusText(phase)` (maps the fine-grained server `phase` to the same display strings the old NDJSON `status` events used to carry, so the UI reads identically to before), and `isJobStuck(createdAtMs, nowMs)` (400s threshold — comfortably past the 300s hard cap plus write/poll latency — a client-side circuit breaker for the case where the background function itself was killed by the platform and can never update its own job row to `failed`).

**Changed — `app/(app)/new/page.tsx` (required to make Level 3 minimally functional at all — the page was broken against the rewritten route until this landed):**
- `handleGenerate()` rewritten from an NDJSON-stream-reading loop to POST-then-poll: `POST /api/quante/generate` returns `{jobId}` almost immediately, then a loop polls `GET /api/quante/generate/status?jobId=...` every 2.5s, running each response through `decidePollAction()`/`phaseToStatusText()`/`isJobStuck()` from `lib/generation-poll.ts`. The old NDJSON version's special-cased "warn at 250s / give up at 290s" timers are gone — they existed specifically to compensate for a stream the function itself might lose connection to; with `after()`, that compensation isn't needed, `isJobStuck()`'s 400s check is the only timeout logic left.
- The Level 2 resume marker is upgraded, not replaced: once the POST response returns a `jobId`, the marker is re-saved with it. A **new polling effect** runs whenever a marker with a `jobId` exists (mount-time load, or a fresh generation that hasn't redirected yet) — polling the exact same status endpoint every 3s, through the exact same `decidePollAction()`, so a page that was just reloaded and a page that never left are running identical logic and can never disagree about what a given job status means. This closes the loop the user asked for explicitly: "po reloadu vidí 'ještě běží' nebo 'hotovo'" — the resume banner now shows a live spinner + the real phase text while a job is running, auto-navigates on completion, and shows a real error message on failure or stuck-job detection, instead of Level 2's one-shot manual "Check status" button (which is kept only as a fallback for markers that somehow never captured a `jobId`).
- New `buildProjectUrl()` helper (shared by both the fresh-generation redirect and the resume banner's "Open finished store" button) — also now forwards `previewUrl` as a `pu` query param, which `StudioClient.tsx`'s existing URL-bootstrap effect already reads but the old redirect never sent.

**Verification:** `npx tsc --noEmit` clean, 0 errors, across all changed/new files. `eslint` clean on every touched file except one pre-existing, already-documented violation in `page.tsx` (`setStageIndex(0)` in the `STAGES` timer effect, flagged and explicitly left out of scope in the Level 2 entry above — confirmed unchanged, not something this change introduced). Full suite (`node --test __tests__/*.test.mjs`) — all 121 tests pass (106 prior + 15 new), no regressions.

**Decision point surfaced, not yet acted on:** `app/(app)/project/[id]/StudioClient.tsx` also calls `/api/quante/generate` — in the `!hasGeneratedOnce` branch of `handleSend()`, for "first generation triggered from Studio chat inside an already-created project" (as opposed to `/new`'s "brand-new store" flow). It uses a shared `consumeStream()` NDJSON-reading helper (also used by `/api/quante/iterate`, which is untouched and still streams NDJSON correctly) and is now broken by this rewrite — that call site will fail against the new `202 {jobId}` response instead of a stream. Deliberately not touched yet: `StudioClient.tsx` is the largest, highest-traffic, highest-risk file in the app (40+ state hooks), and per your own instruction to flag major decisions before proceeding, this is that flag. Options: (a) port the same POST-then-poll pattern into that one call site (smallest, most consistent change, but touches a very sensitive file), or (b) leave `/api/quante/iterate`'s streaming pattern as-is and give this one Studio flow its own small polling wrapper reusing `lib/generation-poll.ts`. Either way the actual generation logic (`runGeneration()`) doesn't need to change — only this one client call site does. Awaiting direction before touching it.

**What Level 3 deliberately does NOT do:** no external queue/service (Inngest or otherwise) — the `after()` pattern was sufficient for the stated problem, so no unused scaffold was built "just in case"; does not fix the `StudioClient.tsx` call site (see above — explicit decision point); does not add a UI-visible distinction between "generation is running because I just started it" and "generation is running because I reloaded onto someone else's in-flight job" (not currently possible to reach as a normal user anyway, since RLS scopes every `generation_jobs` row to its owner).

## 2026-08-18 — Real domain purchase: registrant data, refund-on-failure, /domains page, Studio fix

**Context:** the domain-search/purchase feature first appeared back in the 2026-06-24–06-29 entry above, and by this session had grown a real, working-looking surface — `lib/namecheap.ts` (Namecheap Reseller API client: check availability, register, DNS auto-config), a Stripe Checkout purchase flow, and a webhook handler that registers the domain after payment. 2. **No refund path existed** for that failure — `handleDomainPurchase()` caught the registration error, logged it, set `status: 'failed'`, and moved on. The customer would be out the money with no domain and no automatic refund.

User approved fixing all of this for real (not deferring to roadmap), with an explicit safety-first sequencing: registrant data design approved before implementation, sandbox-only testing (never against live Namecheap/Stripe), refund-on-failure as the first implementation priority, then `/domains` wiring, then confirm the Studio flow.

**Schema/type layer — `lib/domain-registrant.ts` (new)**: `DomainRegistrant` type + `validateRegistrant(registrant, domain)` — required-field checks, Namecheap's `+CC.NNNNNNNNNN` phone format, and a `.eu` → EU/EEA-country-only eligibility gate (real EU regulation: `.eu` registrants must be an EU/EEA citizen, resident, or organisation). ## 2026-08-18 — Fix: "Building…" preview stall (deployment never reaches Vercel)

**Bug (reproducible 2/2 test generations).** After AI store generation and "Push to Vercel", the Studio hung forever on the "Building…" checklist step, no matter how long you waited. In the Vercel dashboard, the two affected projects (`bramble-page`, `kolo-coffee`) both showed a live *project* row but a completely empty *Deployments* list — 0 successful, 0 failed, 0 canceled. So the failure was upstream of the Vercel build: the deployment record was never actually created (or the request was rejected somewhere silent enough that nothing was logged on either side), and neither our server nor our client had any code path that would notice.

**Root causes (three, all needed to reproduce).**

1. **`lib/hosting/vercel.ts` — deploy calls with no defensive validation and a suspicious request body.** `createDeployment` / `createPreviewDeployment` / `createVercelPreviewDeploy` all sent `name: vercelProjectId` alongside `project: vercelProjectId` — passing the raw `prj_xxxx` project ID into a field that Vercel documents as "project name used in the deployment URL" (i.e. it expects a URL-safe slug). Response was consumed as `result.id` / `result.url` with no shape check. If Vercel ever silently rejected or reshaped the response, we happily persisted an empty `deploymentId` into `deployments` and left the client polling a nonexistent record.

2. **`app/api/deploy/logs/route.ts` — SSE polling loop crashed the whole stream on a single 404.** When the SSE `streamDeploymentLogs()` call threw (which it does for a 404 — expected when Vercel never registered the deployment), the fallback poll on lines ~130–150 called `getDeploymentStatus(deploymentId)` with no try/catch. The 404 exception unwound out of the `start(controller)` ReadableStream executor without ever hitting `controller.close()` or sending a final SSE frame. From the client's perspective the stream stayed "open" but silent: `EventSource.onerror` doesn't fire on a stalled-but-alive connection, so the client watched an empty pipe forever.

3. **`StudioClient.tsx` — bootstrap effect, hardcoded checklist, no client-side watchdog.** The `/new`-redirect bootstrap effect (~line 946) only set `previewUrl` and started log streaming — it never touched `showPushToLive` / `hasGeneratedOnce`, unlike the chat `handleSend()` flow which does. Every `/new` user therefore fell into the `!previewReady` render branch, which showed a checklist with `done` values hardcoded to `[true, true, false]` — cheerful ✓ marks for stages that hadn't necessarily happened, and a spinner on "Building…" with nothing to ever un-spin it. And there was no client-level timeout: the only escape hatches were `EventSource.onerror` (which the silent stream never triggers) and the fallback poll inside `onerror` (which therefore also never runs).

**Fixes.**

- `lib/hosting/vercel.ts` — added `toDeploymentName()` normalizer (lowercase, `[^a-z0-9-]` → `-`, capped at 52 chars, prefers an explicit slug over the `prj_` ID), `assertDeploymentResult()` that validates `id` + `url` are non-empty strings before returning, and `logDeploymentFailure()` that logs status/body from thrown SDK errors instead of dropping them. All three deploy functions now accept an optional `projectSlug` and log success (id/url/name/target/file count) so the next time this happens we can see exactly what Vercel returned.
- `app/api/deploy/route.ts`, `app/api/quante/generate/route.ts`, `app/api/quante/iterate/route.ts`, `app/api/quante/fix/route.ts` — pass the derived `slug` into the deploy call so `name` is a real deployment slug, not a `prj_` ID.
- `app/api/deploy/logs/route.ts` — wrapped the `getDeploymentStatus()` and `getBuildError()` calls inside the polling fallback in their own try/catch. Consecutive 404s (Vercel is briefly eventually-consistent right after `createDeployment`) are tolerated for 2 attempts; the 3rd triggers an explicit `build_error` + `stream_end` SSE frame with a helpful message ("Vercel never registered this deployment"). The 5-minute overall timeout now also sends `stream_end` before closing, so the client always gets a terminal event.
- `app/(app)/project/[id]/StudioClient.tsx`:
  - Added `logStreamStage` state (`idle | pushed | building | ready | error | timeout`) driven by the actual events on the SSE stream.
  - Added a 6-minute top-level watchdog (`logStreamWatchdogRef`) that fires if no terminal event arrives. On fire it closes the ES, clears the poll, sets `buildError` with a retry-suggesting message, and flips `logStreamStage` to `timeout`.
  - Bootstrap effect (`/new` redirect) now mirrors the `handleSend()` post-generation branch — sets `hasGeneratedOnce`, `showPushToLive`, `previewReady=false` — so both entry points end up in the same UI state.
  - Replaced the hardcoded checklist `[true, true, false]` with values derived from `hasGeneratedOnce` + `logStreamStage`. On timeout/error the third step flips to "Build failed" (red ×) and a "Rebuild preview" retry button appears instead of the eternal spinner.

**Verification.** `npx tsc --noEmit` clean. Manual runtime verification (fresh generation → deploy → observe checklist advances stage-by-stage; then a simulated 404 by using a fake deployment ID → observe explicit `build_error` + retry button within 30s instead of eternal spinner) is the next step before this ships, per the "test on sandbox, not prod with real credits" guardrail in the fix brief.

**Files touched:** `lib/hosting/vercel.ts`, `app/api/deploy/route.ts`, `app/api/deploy/logs/route.ts`, `app/api/quante/generate/route.ts`, `app/api/quante/iterate/route.ts`, `app/api/quante/fix/route.ts`, `app/(app)/project/[id]/StudioClient.tsx`.

## 2026-08-19 — Fix: preview deploy failure was still silently swallowed

**Follow-up to 2026-08-18.** After the previous day's watchdog/checklist work, a third verification run ("Ember & Oak", following "Kolo Coffee" and "Bramble & Page") reproduced the same "spinner forever" symptom. The Vercel Deployments dashboard again showed 0 rows for the newly-created project even with all 7 status filters on. So the cosmetic layer had improved — the checklist read real state, and a client-side timeout existed — but the actual root cause was still hidden.

**Actual root cause.** `app/api/quante/generate/route.ts` (~lines 331–365) wrapped `createVercelPreviewDeploy()` in a `try/catch` that logged `'preview deployment failed (non-fatal):'` and returned. `deploymentId` and `previewUrl` stayed `null`, but the job row was still marked `status: 'completed'`. Downstream:

- `app/(app)/new/page.tsx`'s `buildProjectUrl()` only appended `did=` when `deploymentId` was truthy, so a failed deploy meant no `did` parameter reached the redirect URL at all.
- `StudioClient.tsx`'s bootstrap effect only called `startLogStreaming(did)` when `did` was present. No SSE opened, therefore the 6-minute watchdog from the 2026-08-18 fix — which lives inside `startLogStreaming` — never armed. The checklist stayed on the "Building…" step with nothing that could ever advance it.
- `previewUrl` in the Studio was set optimistically from the `storeUrl` prop, not from actual deployment success, so the URL bar could look plausible while nothing had ever been deployed.

**Fixes.**

- `lib/hosting/vercel.ts` — extracted a new `summarizeDeploymentFailure(err)` helper (public export) that pulls `.message`, `.statusCode`/`.rawResponse.status`, and `.body`/`.data$` off any thrown Vercel SDK error, fetch failure, or `assertDeploymentResult` throw. `logDeploymentFailure` now delegates to it. Also moved the raw response `JSON.stringify` from `assertDeploymentResult`'s throw branch to *before* validation — so cases where Vercel returns a technically-valid but subtly-shaped response are still visible in server logs, not just outright failures.
- `app/api/quante/generate/route.ts` — the previously-silent catch now:
  1. Logs full `summarizeDeploymentFailure()` output plus the error stack (not just `err.message`).
  2. Persists the failure summary (`message | status=N | body=...`, truncated to 1000 chars) to a new `generation_jobs.deploy_error` column, so a post-mortem doesn't require Vercel Functions log access — the failure reason is queryable directly from Supabase.
  3. Falls back to a completion update without `deploy_error` if the column doesn't exist yet (migration not yet applied) so the job still completes cleanly.
- `supabase/migration-generation-jobs-deploy-error.sql` — new file, `ALTER TABLE generation_jobs ADD COLUMN IF NOT EXISTS deploy_error text`. Idempotent and additive; skipping it degrades cleanly (see fallback above).
- `lib/generation-poll.ts` — added `deployError: string | null` to `JobStatusPayload`, and to the `navigate` variant of `PollDecision`, so the client can thread the failure reason all the way from the DB into the redirect URL.
- `app/api/quante/generate/status/route.ts` — selects `deploy_error` (retries without it on schema error), returns it as `payload.deployError`.
- `app/(app)/new/page.tsx` — `buildProjectUrl()` gained an optional `deployError` argument that sets a new `de=<msg>` query param when present. Both the freshly-completed-poll path and the resume-banner "Open finished store" button pass it through. Added `resumeDeployError` state to hold the value between the poll finishing and the button click.
- `app/(app)/project/[id]/StudioClient.tsx` — bootstrap effect now handles the `de` param: when present without a `did`, immediately sets `logStreamStage='error'` and `buildError` with the failure message, which triggers the same "Rebuild preview" retry UI the SSE-error path already renders. No spinner-forever state is reachable via this route anymore.

**Verification.** `npx tsc --noEmit` clean across all changed files. `eslint` on the touched files reports only pre-existing warnings (unused imports, `set-state-in-effect` findings on lines untouched by this fix). Test-store generation was NOT re-run against production Vercel from this sandbox — the actual Vercel error string, and confirmation that a live subdomain now spins up end-to-end, is still pending until the maintainer runs one more test generation with these changes deployed. This is the piece the fix brief called out: previous rounds have made the *client* survive the failure better, but this round is the first one where the *server logs and the DB row* will contain the concrete reason Vercel refused, so the next test run should finally answer "why". If the reason turns out to be one of the suspects the brief listed (token scope, `name`/`project` shape, missing required field, plan tier), fixing it is a one-line change from there.

## 2026-08-20 — Fix: `@vercel/sdk` response validation was the actual root cause

**Follow-up to 2026-08-19, and the answer to the "why" that entry left pending.** The migration above was applied and a fifth test store ("Grove & Salt") was generated. Its `de=` URL param finally carried a real Vercel error string instead of nothing:

```
Response validation failed | status=200 | body={"accountId":"team_...","creator":{...},...,"deploymentExpiration":{"expirationDays":30,...,"ex[truncated]
```

**Root cause.** `@vercel/sdk` (^1.21.9) parses every HTTP response through a bundled Zod schema before handing it back to the caller. `ensureVercelProject()` (`lib/hosting/vercel.ts`, then ~lines 18–42) called `vercel.projects.getProjects()` / `.createProject()` through this SDK. Vercel's live API was returning a perfectly good `200` with a real, fully-formed project object — confirmed independently, because the project always existed in the Vercel dashboard afterward — but the SDK's bundled schema doesn't recognize some field Vercel now returns (the truncated body cuts off inside `deploymentExpiration`, which strongly suggests a new or renamed field there: schema drift between the SDK's pinned version and Vercel's current API shape). The SDK throws on mismatch rather than returning the data, and it throws *before* any deployment is ever requested. That's why every test store in this whole debugging arc (Bramble & Page, Kolo Coffee, Ember & Oak, Grove & Salt) got a real Vercel *project* and zero *deployments*: the very first Vercel call in the pipeline was failing, silently as far as Vercel itself was concerned, on the client side only.

**Fix.** Rewrote `lib/hosting/vercel.ts` to talk to `api.vercel.com` directly via a new `vercelApiFetch()` helper, mirroring the raw-fetch pattern `streamDeploymentLogs()` and `getBuildError()` already used elsewhere in the same file. Only the 2–3 fields actually consumed (`id`, `name`, `url`, `readyState`) are read from each response, so there is no bundled schema left to drift out of sync with Vercel's API. Applied to every function in the file that previously called the SDK, not just `ensureVercelProject()`: `removeProject`, `setEnvVars`, `createDeployment`, `createPreviewDeployment`, `createVercelPreviewDeploy`, `getDeploymentStatus`, `attachDomain`. The `@vercel/sdk` import is gone from the file entirely (`grep -rn "@vercel/sdk" lib/ app/` returns no remaining call sites, only this changelog comment). All the surrounding 2026-08-18/19 logic — `toDeploymentName()`, `assertDeploymentResult()`, `summarizeDeploymentFailure()`, `logDeploymentFailure()` — is unchanged; it now runs against plain `fetch` responses instead of SDK results.

**Verification.** `npx tsc --noEmit` clean. A sixth test store ("Kiln & Clay") was generated afterward to confirm live — but the `de=` param it produced was structurally identical to the pre-fix Grove & Salt error (same shape, same truncation point, different `createdAt`/timestamps so it was a fresh call, not a cached one). That's expected, not a sign the fix is wrong: **this fix was made directly in the local working copy and committed locally only (commit `4ce1502`) — it was never pushed to `origin/main` and no Vercel deploy ran**, so production was still serving the pre-fix compiled code when Kiln & Clay was generated. `git status` confirms `main` is 1 commit ahead of `origin/main`, unpushed, matching the explicit "don't push, no GitHub credentials in this sandbox" instruction this fix was done under.

If the `de=` error is gone and the Vercel dashboard shows a real row under Deployments for the new project, this bug is closed for good.
